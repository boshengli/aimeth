已有模型类型也随 Patterning 更换；inbox 摘要只携带结构标签。正式比较需单独控制模型多样性与消息内容。

计数要分清。原文的 100 指分析 Agent 格点，不是 100 个群体。100 个分析 Agent＋4 Observer＋1 Chief 共 105 个角色记录。100 组×100 Agent 是另一种 10K 配置，尚未在来源代码中实现。扩容表必须分别记录组数、组内 Agent 数、治理 Agent 数、活跃数、并发数和模型请求数。

从原组织出发的测试顺序

  1. 完成两个可执行组织臂：依 V1 原始 100 格点实现分组、Observer、Chief 和消息/隔离状态；将 V2 的 Patterning、Interface、Vascular、候选保留和反馈落实为行为。
  2. 先做运行契约检查：用确定性夹具检查消息传递、候选溯源、冲突留存、断点恢复和治理预算。这是工程检查，不要求某个模型先解开数学题。
  3. 比较完整架构：V1 对 V2，独立初始化群体为实验单位。另设同预算的独立群体加预定聚合对照，测组织效应；不以随机挑出的末位 Agent 代表群体成果。
  4. 拆出 V2 机制：Patterning 开 / 关 × Vascular 开 / 关；Interface、Observers、Chief 保持一致，用于区分单机制效应及交互。
  5. 在统一资源边界内测试扩容：冻结模型版本、题目、工具、提示、输入 / 输出 token、验证额度、通信额度和截止时间；分别跑配置负载测试与真实模型推理。100、1K、10K 的含义及独立复本数都要明确。
  6. 由独立评估器检查结果：核对精确题目、假设、推理依赖、反例和证明义务。Observer 的 80% 收敛只能作为协调状态，不能当数学证明；共识本身不能取代验证。

主要指标预先定为：规定预算内独立检查通过的群体答案、无效接受率、完整证明义务、候选新颖性 / 多样性、消息与 token 成本、冲突发现 / 修复耗时、失败扩散和恢复表现。前沿 Navier–Stokes 探索要与可验证控制题分别报告。
